# 教训与根因（每条对应一次真实返工；新片结束后把新教训追加到这里）

## 构建产物（最佳实践）
- `public/` 只放本片资产（模板 18MB，bundle ≈38MB）；出 still 只用 `scripts/still.sh`，每组一个固定 tag，改码后 `rm -rf build_dev_<tag>` 再建；不要直接 `npx remotion still src/index.ts …`（会在 $TMPDIR 留临时 bundle，脚本已自动清理）。
- 后台脚本一律绝对路径（shell cwd 会漂移）。

## 分镜写法
- "末 2 帧不离场 + 下一镜头硬切"会被两侧理解成"我不动、你从节拍帧才入场"→ 组界/镜头间 6–8 帧空场（一片里 5 处）。写成"A 末 N 帧归零淡出 + B 首帧起入场"。
- 硬切前离场必须归零：6.7%/帧的 exitFade 末帧还剩 40–57%，动态下会"啪"。用 1−(n/N)^1.5。
- 自下滑入 Δ≈300 在有字幕带的片里会穿过 y637–690（一片里 6 处）。Δ≤120 或侧向滑入 + 前 6 帧渐入。
- 多元素错峰入场别用 GlitchIn（5 个胶囊各自随机闪像掉帧）；用错峰 slide+fade。
- "glitch"一词只写在每镜头一个重点词那一格，否则构建 agent 会给所有文字加闪烁（一片 102 处，用户否决）。
- 分镜给的坐标是参考值，允许构建组按安全区微调；但示例文本、颜色语义、图元必须照办。

## 覆盖层 / 结构
- 覆盖层的压黑/淡出必须在内容之上（SHOTS 数组末尾或 aboveBar），否则末镜头在自己 Sequence 结束时硬切消失。
- 出场动画帧数要够：8 帧 exitAccel(1.2) 只走了 59px/63% 亮度就被硬切；12 帧 440px + 透明度归零才干净。
- HUD 同章相邻条目要无空档（上一条延到下一条 from−1）；进章节卡前 8 帧淡出；HUD 换词与内容大 glitch 错开 4 帧，否则同帧全黑。
- 流程轨末 8 帧淡出，不要一帧消失。
- 预览合成（每组 = 覆盖层 + 本组镜头）让构建组能看到 HUD/流程轨与内容的关系。

## 代码
- kf 首值陷阱：t < 首关键帧返回首值；入场表要以 [镜头起始帧, 画外值] 开头，否则元素提前停在画内。
- Check/Cross 等 draw-on 在 p=0 时要 return null（linecap 会露出一个点）。
- 颜色混合函数要能解析 rgb() 与 hex（嵌套解析出 NaN 导致 25 张卡全不可见）。
- blur σ<0.8 在 Chromium 无效；feConvolveMatrix 走软件路径 0.13 fps 禁用；SVG filter 加 colorInterpolationFilters="sRGB"。
- CJK 行盒 ascent 让墨迹比 top 低 3–7px，居中文字预扣 dy −2…−5。
- 最小字号 22px（QC 量测 ink 高）；上标角标可例外 20px。

## 配音 / 时间轴
- 定稿后不要改词：构建组代码里帧号硬编码。要改先改词再全体重对位。
- TTS 词边界起点与音频 onset 误差 ≈1 帧；检测 onset 时窗口别跨到上一句尾音（会误读 −15 帧）。
- 英文 `|` 切块拼回整句时块之间要补空格（曾把 `powerful|but` 拼成 powerfulbut 送给 edge-tts）；块起始游标也要跳过这个空格。

## 多 agent
- 一个 agent 只派一件重活（构建 5–7 镜头 / QC 一章 / 修 1–2 组）；第二件只派轻活。读过大量图片的 agent 再派重活有 ~30% "input too long" 阵亡。
- API 错误打死的 agent：SendMessage 叫一次可醒；不醒就 TaskStop 重派。
- 构建组会自行合理偏离（换示例文本、加中文全称、改拓扑、缩帧数）；有出处就放行，一句话裁定；把裁定记进 BUILD_NOTES。
- QC 读亮度用 int32（int16 溢出全零）。

# 第二片《eCPM 与广告竞价》（2026-09-07，48 镜头 / 4′16″）新增教训

## 节拍与可读时间（本片最系统性的两类缺陷）
- **出处/依据灰小字不要挂在镜头的最后一个字幕块上。** 分镜表默认把出处写在末拍，结果 40–70 字的灰小字 ≥50% α 只停 0.97–1.7 s，读不完 —— 其中一条是"防止观众把公式误认成现行定义"的纠偏句，等于没送达（QC 判高）。**判据：出处小字必须在所属镜头内有 ≥2.5 s（≥75 帧）的 ≥50% α 停留；写法：f0 挂到镜头的第 1–2 个字幕块**（它是背景依据，不需要跟着解说走）。本片 8 处全部返工。
- **镜头区间 `[句 from−8, 句 to+2]` 开头那 8 帧就是入场预算，别浪费。** 首批元素若等到字幕块起始帧才动，镜头首段会空屏；组界处（前一镜头末 8 帧已归零）会叠成连续 11–16 帧纯黑。本片 9 个镜头中招。**首批元素的 f0 = 镜头首帧。**
- **末拍动画会溢出镜头末尾。** 最后一个字幕块到镜头结束可能只有 20 帧，22 帧的 slideUp、14 帧的 Cross draw-on 都放不进去 —— 成片上表现为"某个元素整个镜头都没出现，到下一镜头首帧突然满态"。派单时给每个镜头算一下末拍剩余帧数。

## `fadeIn` 与首帧
- **`fadeIn(n, len)` 在 n=0 返回 0，用它做镜头首帧入场必然空一帧。** 用 `softOp`（首帧 ≈25%）。
- 更隐蔽的一层：**`softOp(0, 8)` = 25%，白描边亮度只有 65，仍低于"亮度 >70"的空场判据** —— 想让首帧测得出来要写 `softOp(n+1, 6)`（首帧 ≈57%）。同理，紫边 `#A175F1`（亮度 144）在 43% α 下只有 62，也量不到；入场首帧想被量到就得用白边或提高起始 α。
- **不要给自带 opacity 斜坡的组件再套一层 `fadeIn`**（双重淡入）：转场处会凹一两帧。
- **同一元素不要渲染两份**（一份 `SoftIn` 常亮 + 一份 `GlitchIn`）：常亮那份把闪烁完全遮住，实测亮度恒定、闪烁等于没做。要么单实例用 `glitchOpacity(n)` 乘在同一个元素上，要么让常亮那份在闪烁窗口内隐藏。

## 数字的事实合规
- **计数动画的中间值也是"上画面的数字"。** 年份 1995→1998 线性计数会让 1995/1996/1997 清晰可读 4–6 帧；毫秒 0→120 会闪出 `37 ms`/`88 ms`；eCPM 0→30 会闪出 `8`。这些都不在事实清单内。**通则：中间值若是"看起来像事实但没出处"的数字，要么让它不可读，要么不做计数。**
- 让年份不可读要够狠：blur `6.3→1.3px` 中间年份清晰可读；`12→2px` 末段 ≤7px 时倒数第二个年份仍可辨约 2 帧；**最终 `12→9px`（滚动全程 ≥9px）+ 落定帧归 0** 才干净。已封成模板的 `YearRoll`。
- **自建示意算例必须与画面上的其它标注自洽。** 本片两处翻车：① 一个「本秒 ＋2405」的实时计数器，正下方紧跟灰小字「一天几十亿次」—— 两者相差 30 倍；② 价值柱公式算出第 8 根 ≈34，而画面自己标着「≈ 1/5」（应为 24）。**派单前把分镜表里每个自建算例横向验算一遍。**
- 补一条查法：**从源码静态抽取所有会上画面的字面量，和事实清单对账。** QC 是从像素抽帧查的，看不到没被抽到的帧；源码对账把 8 个组一次扫完，本片就是这么抓到那个计数器的（四个 QC 全漏）。

## 字体
- **`Orbitron[wght].ttf` 不含 `¥`(U+00A5)、`≠`(U+2260)、`≈`(U+2248)**（fontTools 可核）。回退链 `'Orbitron','Audiowide'` 要保留 —— Audiowide 同为几何风格，¥ 与 Orbitron 数字是协调的（放大 3 倍实测；换成回退 Noto 反而更不搭）。`≠`/`≈` 直接用 `FONT_HEAVY`。
- **Orbitron 的斜杠零（Ø）在多位数里没问题，孤立成单个 `0` 时会被读成图标**（「0 次点击」成片上读作「Ø 次点击」，示意值直接失效）。**孤立单字 `0` 改 `FONT_HEAVY`；`1`–`9` 字形无歧义可保留。**
- **`Counter` 的默认字族是 `FONT_HEAVY` 不是 Orbitron**，与风格指南「数字用 Orbitron」冲突 —— 本片四个组同时反馈并各自绕开自建了一份。已把默认改成 `FONT_ORB` 并补 `family` 入口。

## 图元与层序
- **旋转类图元的几何要先验算再画。** `GavelIcon` 旧版把槌头画在支点左上方 76 单位、音块在支点下方 101 单位 —— **槌头到支点的距离远大于支点到接触目标的距离，于是 ±26° 的小角度旋转无论正负都只让槌头绕着高处扫，永远碰不到音块**（QC 实测槌头质心 y 507→499 是往上走的）。这不是参数问题。正确造型：接触物水平躺在目标上方、握柄竖直、支点在握柄顶端。
- **落槌类动作不要停在"接触姿态"。** 重写后 `angle=0` 是"竖直细握柄 + 槌头压在音块上"，长时间停在这个姿态被读成橡皮图章/通马桶（两个组独立发现）。落槌后要抬回 −18…−24°。
- **draw-on 的叉/勾不要和箭头挤在同一个 `<Svg>` 里。** 若那个 `<Svg>` 排在卡片组件之前，叉会被卡片的黑底整块盖掉 —— 表现为"这个叉全片不出现"，很容易误判成时序问题。**凡是要压在卡片上的标记，`<Svg>` 必须排在卡片之后。**
- 图元把 `title` 画在**卡外上方**时要在注释里写明，否则有流程轨的章会顶到 rail；`xLabel` 画在 `cy = h−8` 会让 18px CJK 墨迹压死卡下边框（本片三张卡全中）。

## 覆盖层
- **进度条的当前章高亮要切在章节卡起始帧，不是本章首句起始帧。** 否则章节卡在画面正中宣告「02 一次竞价」的那 45 帧里，底部进度条还高亮着上一章，两处信息矛盾。
- **流程轨当前步的切换不要做成 1 帧硬切**（灰底↔紫底同帧翻转），与 HUD 换词「一律 8 帧淡入」不一致。加 7 帧交叉过渡。
- 流程轨入场的上浮 Δ 要 ≤22：Δ40 会让胶囊下沉到 y184，越过"有轨镜头内容不进 y<175"的空间契约。
- 片尾 `EndingTop` 的淡入帧数决定"末段纯黑"有多长：20 帧只剩末 11 帧纯黑，改 10 帧才有末 19–21 帧。
- **片尾压黑的起始帧会吃掉末镜头的收尾动作。** `endingFade=30` 时压黑从"末句结束 −30"开始，本片的收尾敲槌原本落在其后，全片最后一个动作完全看不见。派单时把末镜头的动作排进压黑之前，或调小 `endingFade`。

## 多 agent
- **tmux/fork 有上限，且是全机共享的。** 本机同时开着 13 个其他 Claude 会话，派到第 8 个构建组时 `respawn pane failed: fork failed: Device not configured`，两次重试都起不来 —— 主会话只能自己顶下一整组（6 个镜头）。**派单前先 `ListAgents` 看全机占用；预留 1–2 个 pane 给后续的 QC/修复轮；完成的 agent 及时 TaskStop 释放。**
- **"边查边 append"对 QC agent 是硬要求，不是建议。** 本片一个 QC agent 攒到最后写盘，跑了一小时零产出、消息也不回，只能 TaskStop 重派（重派时把主会话已查到的结论直接给它，并让它 QC+修复一并做，反而更快）。
- **不要照抄 agent 的自评。** 本片抽验发现：一个组自评"中间年份模糊不可读"，实际出图清晰可读（它自己在复盘时也承认"§6 偏离①的自评过于乐观"）；另一个组报告"已改为调用共用 exitOp"而磁盘时间戳看起来更早（这条查下来是我误读，报告是对的）。**结论：报告要抽验，但也别急着断定 agent 说错了 —— 先把证据看全。**
- **构建组会发现分镜表本身的错误，要鼓励并快速裁定。** 本片三条最有价值的改进都来自构建组：价值柱公式与画面标注矛盾、年份转盘的事实合规漏洞、以及据此主动偏离不给毫秒数做计数。裁定时把它推广成全片通则并写回分镜表，比只批准单点改动值钱得多。
- 主会话自己要留一手**与 QC 互补的检查**：帧覆盖静态分析（帧区间/空洞/重叠）、源码字面量与事实清单对账、闪烁白名单源码级计数。这三项都不用渲染，几秒钟跑完，而且抓到的都是 QC 从像素查不到的问题。

## 风格传递（2026-09-08 复盘：用 skill 做的《广告竞价》vs 样片《RAG》）
- **skill 写了禁令没写审美驱动**：安全区、白名单、归零、节拍全传过去了（新片在这些纪律项上甚至更好），但「画多大、谁发光、高光时刻怎么编排」只在做样片的人脑子里 → 新片主体中位高度 172px vs 219px、29% 时长最大物体 <110px、主角全是无光白线框、高光时刻用「胶囊 + 图标 + 一行字」应付。修法：`composition-and-light.md` 硬规则 + 分镜表加「主角·尺寸」「光」两列 + 高光时刻清单。
- **样片源码没人读**：8 个构建组 BUILD_NOTES 零处提到 shots_src，光效图元（LightBar/HaloRing/GhostText）留在样片组内文件里没进模板 → 新片一个组重新发明了 LightBar。修法：光效图元升进 `template/src/fx.tsx`；模式表最后一列给源码路径，构建 prompt 从「可参考」改成「必读」。
- **QC 只查缺陷不查「空 / 小 / 暗」**：四轮 QC 全过，画面还是小而暗。修法：`scripts/frame_metrics.py` 量最大物体高度 / 主角区柔光 / 碎片，写进 QC 判据与终检。
- **运镜被本文自己压掉了**：旧版 build-rules 写「静态镜头为主」，结果样片和新片都只有 2.2–2.5 次/分钟、零次推近，而风格来源的原片是 6.6 次/分钟、平均 16 帧、含推近拉远视差。修法：`CameraRig` 组件 + 运镜预算（每章 ≥3）+ 分镜表运镜清单。
- 两片动效数量、节奏、柔光总面积几乎相同（每帧变化 0.47 vs 0.56，事件 72 vs 76 /分钟）——**差距不在「动得多不多」**，别往加动效的方向修。

# 第三片《电影运镜》（2026-09-08，50 镜头 / 4′00″，一轮 QC 后 高0/中0/低14）新增教训

## 当主题本身是几何的：先造一个真的，别用 CSS 假造
- 本片的中心论点是「透视只由机位决定，与焦距无关」。**如果画面用 `scale` 假造，推近和变焦会长得一模一样，整章等于讲错。** 所以在 `ui.tsx` 里实现了真的小孔成像投影（`project3` / `FrameScene` / `camOrbit` / `camDollyZoom`），推 = 只改 `cam.z`、变焦 = 只改 `cam.f`、摇 = 只改 `cam.yaw`…… QC 逐像素验证：SC37 两框人物 275/275px 相等而背景门高 197 vs 158px（差 20%），SC38 人物全程恒 164px 而后墙 506→360px。**论点因此是"画面证明"的，不是"旁白声称"的。**
- 通则：**凡是"两种做法看起来像但其实不同"的主题（推 vs 变焦、tilt vs 升降、真长镜头 vs 假长镜头），都必须让底层机制真的不同**，否则观众看到的两幅图会一样。
- 反面成本：真投影会带来一整类新缺陷（画框变空、物体越出画框、人物尺寸出安全带），见下条。

## 派 8 个 agent 之前，先用探针把共用系统跑一遍
- 我先写了一个 `_probe.tsx`，一帧一格渲染 8 种相机状态，出 8 张图看一眼。**当场抓到两个会让 8 个组集体做错的问题**：① `pitch=−22°` 时画框几乎全空（人物 180px 但画框 332px，人整体在框内，pitch 一动就把人扫出去只剩地板）；② 默认 `personZ=520` 时人与后墙只差 165cm，推 vs 变焦的背景差别只有 12%，**肉眼看不出来**——必须把人挪近到 `personZ=320` 才有 26% 的差别。
- 这两条如果不提前发现，就是 SC17 与 SC37/SC38 三个镜头（含两个高光时刻）集体报废。**探针成本 10 分钟，返工成本 3 个组。**
- 探针的产物要变成分镜表里的**「相机参数速查」实测表**（`cam.z` → 人物画面高的对照表 + 安全带 150–300px），派单时直接给数字，不要让每个组自己踩。

## 跨组一致性：把常量放进共用层，不要让 agent 互相对齐
- v1 里我一开始让「G6 建矩阵、G7 复用」「G5 复用 G3 的间距标注」——结果 G7 要跨组 import、G6 与 G3 各存了一份逐参数复制的 `PinCross`，并且 G3 一改 G5 就跟着变。
- 更好的做法（本片后半采用）：主会话**先把跨组共用的东西放进 `ui.tsx`**——`LAYOUT`（版式坐标）、`frameInner`、`frameMarks`（门/人/信的包围盒，用同一投影算）、`ACTION_WORDS`、`softOp` / `exitZero` / `mix` / `Vignette` / `MarkBox`。八个组直接 import，天然一致，零协调成本。
- 教训的具体形态：**`softOp` 被四个组各写了一份，四份公式还不一样**（G1/G2 的在 n=0 返回 0，靠调用处传 `n+1` 补偿；G3/G4 的把 +1 写进函数）。协议里反复写「用 softOp 不要用 fadeIn」却没在共用层提供它，等于逼每个组自己发明。**协议提到的工具必须在共用层真的存在。**

## 高光时刻的"清场 → 扫光"开场本身会被判空场
- v1 两条"高"都是这个形态：SC12（论点型）前 79 帧只有一条舞台光线 + 一轮扫光细带，最大物体 ≤46px；SC40 前 66 帧只有五个未激活的暗框 + 一枚胶囊。
- `composition-and-light.md` §6 写了「扫光 / 舞台光线阶段（内容区柔光 ≥10000px²）不算空场」——但**一轮扫光的柔光面积够不上 10000px²**（实测 5004px²）。于是"按编排做的清场开场"反而触发空场判据。
- 修法有二，最好同时做：① **扫光加到三轮**并把 `StageLine` 柔光半径加倍，真正落进豁免区；② **在第 1 个节拍就给一个临时主角**（本片把上一镜的大字承接过来缩到 120px，或把该拍的关键词直接做成 96px 大字，下一拍再缩小让位）。
- 通则：**登场型/论点型高光时刻的前 60–80 帧要单独算一遍"这几帧最大物体多大"**，别假设"清场 + 光效"能自动过关。

## 片尾压黑 vs 最后一个字幕块：要算，而且要算两次
- lessons 里已经有「片尾压黑会吃掉末镜头收尾动作」，本片踩的是它的**升级版**：不是动作被吃掉，而是**全片结论大字只有 6 帧（0.20 s）满态可读**。
- 成因是三件事叠加：末字幕块起于 f7067 → `GlitchIn` 12 帧（**其中 7 帧字是灭的**）→ 压黑 f7085 起吃亮度。18 帧的窗口里能读的只有 6 帧。
- **判据**：`(S_last.to − endingFade) − 末字幕块起始帧 ≥ 30 帧`，否则结论读不完。`GlitchIn` 的 12 帧里有一半是"灭"的，等于**实际可读时间只有窗口的一半**——用 glitch 做收尾大字时要按双倍预算算。
- 本片的修法：把**整句**结论提前到倒数第二拍（f7043）一次入场，末拍改由"光在动"（光环波纹加密 + 柔光脉冲 + 描边渐显）承担可察觉变化。**注意提前的落点不能压在白闪帧上**——QC 发现我原本提议的 f7040 正好是一段运镜白闪的首帧，glitch 落上去会读成"闪坏了"，改 f7043。
- 派单时就该给末镜头算这张表：末字幕块起始帧 / 压黑起始帧 / 中间有没有白闪 / glitch 的有效可读帧数。

## 变换缩放会把字号带下去
- SC34/SC39 的十个动作胶囊用 `scale(0.72)` 做承接位移，26px 的字变成 **18.7px**，跌破「最小字号 22px」。QC 从像素查不出来（它量的是 ink 高度，18.7px 的 CJK ink 约 14px，容易被当成"小标签"放过），是构建组 G7 自己算出来报的。
- **通则：凡是整组 `scale`/`transform` 的地方，把里面所有字号乘一遍缩放系数再对照 22px 下限。** 修法是改源头字号（26→31，31×0.72 = 22.3），不是改缩放。

## 双联版式：左右两半必须真的是同一台相机
- 本片主版式是「左俯视平面图 + 右取景框」。v1 里平面图把门画在**左墙**，而画框里门在**后墙**——两半互相矛盾，而且平面图的视锥里根本没有门。QC 一眼看出来。
- 成因：`roomAnchors()` 是我按"平面图好看"手写的示意坐标，`SCENE` 是按世界几何写的，两者从没对齐过。**修法：让平面图的门位由 `SCENE` 反算**（世界 x=−245 在 x∈[−440,440] 里的归一化位置 0.2216），门画到上墙。
- 但也要认清代价：**把平面图改成 `SCENE` 的严格投影会移动所有组已调好的视锥角度**。本片只做了低风险的一半（门位归正 + 信封缩小），剩下的（相机朝向、视锥张角、房间比例）作为"示意图不是严格投影"记进交付说明。**这类改动要么在派单前做完，要么就承认它是示意图。**
- 同一个图元在不同组里颜色不一致也属这类：`FovCone` 默认色是紫，G5 显式传了灰、G6 用了默认 → 第 3 章上下半视锥颜色不同，还是 SC35「紫色碎片≥8」的主因。**默认值要按规范设（配角不发光 → 默认中性灰），不要让"传不传参数"决定风格。**

## 房间/场景几何要先想清楚"镜头会转到哪"
- `SCENE` 一开始只有后墙、且只到 x=±440，没有侧墙。结果**大角度摇（|yaw|≳8°）、环绕、横移时画框前导侧露出成片纯黑**——G3 被迫把甩镜落点从 +42° 收到 +22°，G4 被迫把 SC19 两框的 yaw 差从 60° 收到 26°，而 G6 的 SC32 要环绕 55°（θ=55° 时后墙右缘只到画框 61%，39% 是空区）。
- 补两面侧墙（逐段画 + 逐段判可见性，推近到侧墙之后能优雅退化）一处改动同时救了三个组，**而且侧墙的透视收敛线反而成了「横移有视差」「背景独自被抽走」最好的证据**——G5、G6 都主动回报效果变好。
- 通则：**场景几何要按"最极端的那次运镜"来设计**，不是按默认机位好看来设计。派单前把所有运镜的角度/位移列一遍，问一句"这个角度下画框四边各是什么"。

# 第五片《TLS 1.3》（2026-09-11，15 镜头 / 63 s）新增教训

## 「柔光呼吸不算」——SC11 用 2.3 s 静止换来的最小代价一课

- §9 判据是**面积归一化**的：内容区降到 320×180 后取逐帧灰度平均差，<0.35 记静止。这个口径**奖励「大面积、微小变化」，几乎不给「小面积、大幅变化」分数**：
  - 整屏卡片滑入 → 0.4–2.1（轻松过）
  - 3 px 虚线 draw-on / 7 px 红叉绘制 / r=6 光点沿弧跑 → 0.07–0.25（等于没动）
  - 单个字形 ±6 px / 40 帧浮动 → **0.94 px/帧**，全分辨率只有 ~120 px 变化 → 读作「真静」
- 所以**靠「元素自己动一点」过 §9 是靠不住的**——尤其当镜头内容本身就是细线 / 小点 / 小字（SC11 正是）。
  分镜 §9 那句「**柔光呼吸不算**」是硬约束：把光晕呼吸从 ±15% 加到 ±60%，读数只从 0.071 涨到 0.089，**白做一轮**。
- **可靠解法只有运镜（整帧慢推）**：1.0→1.08 贯穿 99 帧 = 每帧亚像素整体位移，让全画幅每条边缘都产生 AA 微变，累加即达标。SC11 实测 **78% → 6%、2.3 s → 0.2 s**。
- 由此得一条**分镜写法规则**：写镜头「持续」句时，若该镜头内容以细线 / 小点 / 小字为主，**必须同时声明运镜**（§6 末条已允许在「持续」句内声明），否则规格必然过不了自己的 §9。SC11 原规格只写了「光点跑（1248 才出现）+「?」浮动 ±6 px」，实测 1185–1253 连续 69 帧静止——这是**规格欠配，不是实现缺陷**。遇到这种：**改分镜表 + 改实现，两处都留痕**。
- 组级 `motion_check`（step=3、0.5 倍）会**漏报**：SC11 组级报 1.1 s，step=1 逐帧复测是 2.3 s，且 `longest-run` 起点差 14 帧。**定位动效缺陷必须 step=1 逐帧量**。

## `text-shadow` 不支持 spread：一条静默失效、tsc 不报、静止帧也看不出的坑

- `ui.tsx` 四个 `GLOW_*` 常量**全是 `box-shadow` 形态**（含 spread），例如
  `GLOW_ORANGE = '0 0 40px rgba(243,95,69,.75), 0 0 100px 10px rgba(243,95,69,.25)'`。
- CSS 的 `text-shadow` 只有 `x y blur color` **三个长度**。一旦值里出现第 4 个长度，**整条声明被判无效并整条丢弃**（不是只丢掉那一层）。
- 于是把 `GLOW_ORANGE` 递给 `CText` 的 `shadow`（→ `textShadow`）**从未渲染过一次**；而它当 `boxShadow` 用（SC05、`Box` 的 `glow`）完全正常——所以能长期潜伏。SC11 的「?」光晕就是这么「消失」的。
- **定位手法（零图像 token）**：在元素周围取环带求灰度均值，逐帧看是否随 `qGlow` 变化。实测恒为 7.56–7.63 → 立刻锁定渲染层而非数值层，比看图快且更确定。
- 修法：展开成合法的 3 长度 `text-shadow`。建议在 `CText.shadow` 上加护栏（含 4 长度 → `console.warn`）或提供 `glowText(k)` 助手——**否则每个构建 agent 都可能踩一次，而它是隐形的**。

## `selfcheck.py` 的两处「惯例假设」bug（改完从 12 条告警降到 0，并暴露出一个真缺陷）

- **闪烁白名单只认枚举式**。分镜有两种合法惯例：A) 枚举式「**闪烁白名单**：SC01 词 ·…。**不在表内…」；B) **内联式**（在每镜头「动效」列直接写 `GlitchIn` / `glitch`）。原实现只解析 A，凡用 B 的影片会把 15 个镜头**全部误报 ✗**。已改为两者都支持（A 优先，缺省时按内联从「动效」列反推）。
- **[literals] 把 JSX 属性片段当画面字符串**：引号跨行误抓出 `fontSize={30} sw={2} style={{filter:` 之类。已加过滤器——含 `{}<>;=` 或形如 `, transformOrigin:` 的一律跳过；字体名（从 `public/fonts` 反推）也不算画面文本。
- **修检查器的回报**：白名单一修好，立刻报出 `SC02 GlitchIn×0（白名单「握手」）`——分镜「动效」列写了「**Pill glitch**」（该镜头唯一重点词），而 `SC02.tsx` 里那个「钥匙」Pill 走的是 `SoftIn`，**根本没闪**。改 `SoftIn → GlitchIn` 即修（两者都是全画幅绝对定位容器，替换后布局语义一致）。
- 结论：**检查器的假阳性会把真阳性一起埋掉**。告警全是噪声时人就不再逐条看了——宁可花一轮把解析器修准。

## 单镜头动效迭代：别为调一个镜头的动效反复整片重渲

- 整片重渲 ≈ 1.5–4 min，而 `scripts/mc_one.py`（本片新增，已进模板）只建一次 bundle、只渲目标帧区间，**一轮 ≈ 20 s**，且默认 step=1 出逐帧曲线。
- 用法：`python scripts/mc_one.py G3 1155 1254 --profile`（首次建 bundle）；源码未改时加 `--reuse` 复用 bundle → **11 s**。
- 实测用它把 SC11 从 78% 迭代到 6% 只花 4 轮（≈80 s），等价于 4 次整片重渲（≈8 min）。
- 坑：Remotion `--sequence` 的产物命名是 **`element-<frame>.jpeg`**（连字符，不是 `f_<frame>.jpg`），帧号是**全局 0 基**：传 `--frames=633-1153` 实际渲的是真实帧 634–1154，产物名 `element-0633.jpeg`…`element-1153.jpeg`。→ 帧号正则用 `(?:element|f)[-_](\d+)`，且 **`element-N` 的真实帧 = N+1**（2026-09-11 实测修正）。原表述会让人把 N 当真帧号，导致报出的最长静止段区间**全部偏 1**。
- **补零位数不固定**（这条踩了两次）：不是固定 4 位，而是 **= 该次渲染「最大帧号」的十进制位数**。实测：`634–1154` → `element-0633`（4 位）；`905–995` → `element-904`（3 位）；`1155–1254` → `element-1154`（4 位）。→ **不要硬编码 `%04d`**，探针一律先 `glob('element-*')` 再解析整数（拿 `element-794` 去开 `element-0794` 会 FileNotFound）。

## 沙箱 safe-delete 与渲染脚本的冲突（Windows 移植）

- `render.py` 会在开头清空 `fin_frames`、结尾清 `build_full`；两处都是 >50 项的批量删除，会被 safe-delete 拦下并**中断脚本**（`rc=1`，且 `build_full` 的清理失败会让 stdout 缓冲丢失，看起来像「什么都没做」）。
- 判据：看 `renders/*.mp4` 的 **mtime** 与 `sheet_*.html` 是否生成（`sheet 32 cells` 打印出来就说明主流程已跑完，`rc=1` 只是收尾清理被拦）。
- 稳妥做法：渲染前把 `fin_frames` / `build_full` / `build_dev_mc*` **全部改名挪开**（`.stale` 后缀，不删），跑完再让脚本自己建新目录。

# EXP-01 第二次收尾（2026-09-11 晚）：补跑第三根质量轴，抓到一个真回归

## frame_metrics 不是冗余：它抓到了 QC 与 selfcheck 都没抓到的回归

- 背景：C2 判定时只跑了 `motion_check`（运动）+ `selfcheck`（结构），**`frame_metrics`（构图/光/尺度）两侧都没跑**（遗留第 3 条）。补跑后立刻出现一个真缺陷：
- **SC08「低:主角无光」**：C2 重建时把 C0 的 `ServerIcon glow` 换成了 `RackIcon` —— **新图元自带 `glow?: boolean`、默认 false，而调用点没传** → 220px 的立柜主角丢了紫柔光。C0 版是有光的，所以这是**重建引入的回归**，不是布局差异。修法就一个词：`<RackIcon … glow />`。
- 教训一：**每部片都要跑全部三根轴**。`motion_check` 只度「动没动」、`selfcheck` 只度「结构对不对」，两者对「光是否跟着主角」完全无感；一个**可选 props 没传**不会报任何错，只能靠画面度量或人眼。
- 教训二：**换图元要逐项对 props**。本次 `ServerIcon glow busy` → `RackIcon glow lit`：`busy` 换了名、`glow` 直接忘了。重建镜头时「新图元长得一样」是最危险的错觉 —— 先 diff 两版的 props，再动笔。
- 教训三（不削弱判据原则）：判据报了，**先证是不是真缺陷，但不要顺手改判据**。数值探针证明「合成钥匙的光没丢」（992 帧柔 21,542/紫 19,238 vs C0 22,503/19,339，−4%），只是 C2 把钥匙激活推后了 18 帧；但同一镜头**另一个 220px 主角（立柜）确实没光** → 判据命中的是真实违规（只是理由与「光丢了」不同）。改的是画面，不是阈值。

## frame_metrics 的两条读法（本次实测）

- **「主角区柔光」取的是「最大物体」的邻域** → 一个镜头里有两个大物体时（如 SC08 的立柜 220 + 合成钥匙 170），它挑大的那个；光在小的那个身上就会被报「主角无光」。所以这条命中时**必须先用窗口探针确认光在谁身上**，再决定改画面还是改布局。
- **确定性可当作度量器的自检**：本次 C2 只重建了 G2，另 10 个镜头两侧源码相同 → `frame_metrics` 两栏**逐位相同**（含中位数），证明脚本无随机性、可以逐镜头配对对比。以后每次分档对比都顺手核一遍未重建镜头是否与上一栏完全一致（对不上就是度量器或输入出了问题）。
- 耗时：全片 1,896 帧、`--step 4`，两侧各 ≈110 s；只跑本组加 `--shots SC06:634-776,…` 可大幅省时。

## 生成物手改会脱节：`分镜表.md` 是函数输出，不是文档

- `render_storyboard.py` 只做一件事：把 `script/storyboard_src.md` 的令牌换成帧号 → **`分镜表.md` 完全是 `storyboard_src.md` 的函数**。本轮在生成物上直接改了 SC07/SC09/SC11 三处（含需留痕的「规格修正」），与源比对时暴露出**三行脱节** —— 任何一次重生成都会默默抹掉。
- 规矩：**改规格只改 `script/storyboard_src.md`，改完重生成**。拿不准就先做一致性校验（自己跑一遍令牌替换，与磁盘上的生成物逐行 diff；不一致的那几行就是「只手改过生成物」的）。
- 回灌手法（保留令牌不丢）：对脱节行做**字符级 SequenceMatcher**，只把生成物里多出的片段（`insert`/`replace` 的 opcode）按位置插回源，**不要整行照抄**（照抄会把 `{S07.from-8}` 变成硬编码 768）。
- 同时守住表格结构：本次把留痕文本追加到了行尾 → 该行变成 **8 格**（表头 7 格），表格坏掉。规矩：**留痕一律追加在「动效」格（第 5 格）末尾**，形如 `…**（【规格修正·构建时】…）`，与 SC07/SC09/SC11 一致；改完必须数一遍每行格子数。
- 留痕文本会**增加读清单**（本轮基线 39,290 → 39,388、G2 9,315 → 9,412）→ **读数必须在留痕全部回灌之后再测一次**，否则写进文档的数字会偏小。
- `selfcheck.py` 原来**没有退出码**（恒为 0），脚本里无法当门禁 → 已改为 `sys.exit(1 if problems else 0)`。

## frame_metrics：「主角区柔光」与「紫色碎片」对「大主角」是**耦合**的

- 判据物理（读自 `frame_metrics.py`）：`低:主角无光` = 主角区柔光中位 **< 800 px²**；`低:紫色碎片≥8` = **实心紫、不膨胀、≥80 px 一块**、排除柔光雾，中位数 ≥ 8。
- 实测（SC08 的 121×220 立柜）：**无光**时紫碎片 7；任何足以把柔光抬过 800 阈值的紫光都让它变 **10** —— `GLOW_PURPLE` 双层（柔光 15,751）与 `GLOW_PURPLE_S` 单层（柔光 9,821）**紫碎片都是 10**。
- 结论：**守住 §7「光跟主角」就必吃一条软标记**（紫光在主体边缘必然凑出 ≥80 px 的实心紫环）。→ 这时选**与同片同类元素一致的常量**（本例 SC01 用 `glow` prop），不要为了消一条软标记去削弱主角光、也不要顺手改阈值。
- 该判据的合理修法（**本轮未改**，留给后续）：把「紫色碎片」改成**排除主体邻域**再计数，否则每部「大主角 + 紫柔光」的片都会吃一条假软标记。
- 另一条读法：**「主角」= 「最大物体」单选取** → 一镜有两个大物体时（220 立柜 + 170 钥匙），光在小的那个身上也会报「主角无光」。命中该条时**先用窗口探针确认光在谁身上**，再决定改画面还是改布局。
- 工具衔接：**`mc_one.py` 的产物是 640×360**（写死 `--scale=0.5`），而 `frame_metrics` 要 1280×720 → 想走快路必须先 `mc_one … --scale=1`（已加开关，默认仍是 0.5；静止率判据不受影响）。转帧时 `element-N` → `f_{N+1}.jpg`。

# 追加：判定「两版成片差异在哪些镜头」的正确做法（2026-09-11 实测）

- **直接从成片解帧比对，不要翻残留帧目录**。本次 `fin_frames*` 累积了 7 个同名 1896 帧目录（见下条），只看目录名无法判断哪个属哪一版；而从 `renders/*.mp4` 解帧比对是**无歧义**的。
- 手法（1896 帧 ≈1 s 跑完）：`ffmpeg -v error -i x.mp4 -vf scale=320:180 -pix_fmt gray -f rawvideo pipe:1` 开**两路并行** Popen，逐帧 `read(320*180)`，算「平均绝对差」与「差异像素占比」，超过阈值（本次用 mad>0.30 或 frac>0.0015）即记该帧不同。
- 结果样例：C0 vs C2 两版**差异严格限于帧 641–1154（21.37–38.47 s）**，恰好是唯一被重建的那 5 个镜头；其余 1382 帧逐像素一致。→ 这就是「整片对整片比较是否有意义」这个问题的直接答案，比任何抽样都硬。
- **「挪开」逻辑别用前缀匹配**：`for d in os.listdir(R) if d.startswith('fin_frames')` 会把上一轮改出来的 `fin_frames.stale` 再改一层，几轮后攒出 `fin_frames.stale.stale.stale`。改法：挪开时 `if '.stale' in d: continue`，或统一归档到 `_runs/<版本>_<时间戳>/`。

## 「全片独立生产」怎么证明：逐帧像素差异是最强证据

当要论证"这一版成片没有复用上一版"（而不是只改了某几个镜头）时，三重证据按强度排序：

1. **逐帧像素差异（最强）**：两版 mp4 各用 ffmpeg 解码成**同名同序** jpg（必须同分辨率，别缩放，缩放会制造伪差异）→ 逐帧 numpy 绝对差。判据 `mad>0.30 或 frac(>25 灰阶)>0.0015` 记为"实质不同"。
   - 本次结果：实质不同 **1619/1896（85.4%）**、一致 277；连续不同区间 **8 段横跨全部 15 镜头**；**没有一个镜头是整段一致的**。
   - 判读的关键不是百分比，而是**一致帧的分布**：若"只改了几个镜头"，一致帧会形成若干**完整镜头区间**；本次一致帧占比 0–11%，且集中在 HUD / 幕底星点等外壳层（两版共用的固定元素）——这才叫"全片独立"。
   - 对拍基线很说明问题：上一轮"仅重建 G2"的版本，差异**只出现在 21–38 s**。
   - **阈值敏感性**：边界帧会计数漂移，两次独立跑得到 1618/278 与 1619/277（**±1 帧**）。报告里要写明这一点，别把 ±1 当结论变化。
2. **源码字符相似度**：`difflib.SequenceMatcher` 比新实现 vs `.c0` 备份。本次 0.06–0.28、非空重合行仅 8–13 行（全是 import 样板）→ 没抄。
3. **作者侧旁证**：各组的 `BUILD_NOTES.md` 是全为新写、含独立的 per-shot 读数与探针记录。

> 顺手记住：**"成本线性可加"要单独验证**。上一轮只测了 G2 单组（−76%），无法回答"三组同时上 C2 会不会因组间耦合而退化"。本轮三组各自达标（−78% / −76% / −76%，全片 −77%）→ 答案是**不会**。多组并行的实验，务必在"全片尺度"上再报一次总账。

## 度量前的第一件事：确认抽帧目录真的是这部成片的

本轮复核基线时抓到一个**污染源**：某个 `frame_metrics` 结果的数据源是 **`fin_frames.stale2`** —— 一个多版本混装的残留目录，**不是目标成片的解码**。表现是同一个镜头在两个 C0 度量文件里数字不同（SC07 紫碎片 8 vs 12、SC14 9 vs 10、SC15 8 vs 4），标记总数因此差 1 条（低 14 vs 低 13）。**数字"看起来合理"，不会报错。**

根因是"挪开旧产物"的逻辑：
- `fin_frames*` 在本项目里累积了 **7 个同名残留目录**（`fin_frames` / `.stale` / `.stale2` / `.stale.stale…`），**命名无法区分是哪个版本**。
- 早期「挪开」用前缀匹配（`d.startswith('fin_frames')`），几轮下来攒出 `.stale.stale.stale`，于是新旧帧混在同一棵树下。

**规矩**：
1. **每次度量都从成片现解帧**，解到**带版本名的新目录**（如 `_runs/C0_frames`、`_runs/C2F_frames`），**不要复用任何 `fin_frames*` 残留目录**。
2. 解完**立刻核一次来源**（`a2e-cost/verify_frames_source.py` 的做法，2 秒）：`ffmpeg` 从 mp4 现解几个探针帧与目录同名 jpg 比 —— **同源 mad < 0.25**（只差 jpg 有损误差），不同源会差几十级。
3. 归档旧产物用 `_runs/<版本>_<时间戳>/`，别用 `.stale` 前缀叠加。

**推广**：凡是"从渲染产物反推数字"的度量（`frame_metrics` / `motion_check --frames` / 逐帧差异），输入目录都算**实验数据**，必须先证明它属于哪一版。**度量器再确定，也救不回喂错的数据。**

## 下「通过」结论前，先逐条对着预注册判据列「覆盖 / 无覆盖」

**本轮最严重的失误**：C2 全片重建后我报了「通过」，但实验方案 §四**事先定好**的回退判据里有一条是
「出现 C0 没有的**新缺陷类型**（如遮挡、溢出、节拍错位）→ 回退」——**而遮挡这一类，我的三根轴一条都测不到**：

| 轴 | 能看到「元素间遮挡」吗 |
|---|---|
| `motion_check` | ✗ 只测逐帧有没有在动 |
| `selfcheck` | ✗ 帧覆盖 / 白名单 / 字面量 / 生成物脱节 |
| `frame_metrics` | ✗ 只测**单个**最大主体的尺度·柔光·碎片数，**不做元素两两相交** |

人眼一看就报了遮挡。**「通过」变成了"在我测得到的范围内通过"——这不是实验意义上的通过。**

**根因不是疏忽，是判据类被拿掉了**：成本方案的判据表第 1 行本就写着
`| §1 遮挡/溢出/字号 | agent 看图 | 元素 bbox vs 安全区 |` —— 这一类**原靠 agent 看图覆盖**，
替代它的静态检查器**从未实现**（`layout_audit.py` 是半成品：只覆盖越界、不覆盖元素重叠、自评精度 29%）。

**规矩（写死）**：下"通过"之前，**逐条抄出预注册判据，每条标注「由哪个轴覆盖 / 无覆盖」**。
凡标「无覆盖」的判据，**不得在结论里默认通过，必须显式写"未验证"**。
> 与"假阳性会把真阳性一起埋掉"同源，但更危险：**无覆盖是无声的**，假阳性至少会响。

**同时记住**：压缩会**优先伤害那些只有人工覆盖的判据**。
C2 在 §6「持续动作」（有 `motion_check` 机器门禁）上做得比 C0 更狠（静止率 6.7% vs 14.3%），
代价却落在了 §1「遮挡/溢出」（只有人眼看）上 —— 典型的 Goodhart：
**被量的指标被优化，没被量的指标被牺牲；而压缩恰恰是"减掉测量手段"的动作。**

## 压缩档位的真正代价：视觉验证带宽，不是读清单

对比 `prompts.md` 两条派单模板（C0 用第 9 行那条；**C1 与 C2 同用第 15 行那条**）：

| | C0 构建组 | C2 构建组（**C1 与此完全相同**） |
|---|---|---|
| 每镜头 still 张数 | **≥6** | **2** |
| still 分辨率 | 全尺寸 1280×720 | **0.25 档 320×180（像素 1/16）** |
| 看图时机 | **每写完 1 镜就出图自检（闭环）** | **全组写完一次性看（开环）** |
| 参考帧 | contrast_sheet + **≥6 张** `ref_*.jpg` | contrast_sheet + **≥4 张** |
| 图元认知 | **`cat src/ui.tsx` 通读** | 只给签名索引，**明文"不要通读"** |

**单镜头视觉信号量差约 15–20 倍**，且一个闭环一个开环（开环的修法代价最高，agent 会倾向少报）。
→ 这条能同时解释用户报的**两件事**：「出现遮挡」（看得到就会发现）+「细节不够完善」（有标尺才知道差在哪）。

**关键推论（排档位时必记）**：
- **C1 与 C2 的差距只在读清单**（先验知识）；**still 协议两者相同**。
  → 所以**跑 C1 是一个干净的判别实验**：C1 干净 ⇒ 病灶在读清单；C1 仍有遮挡 ⇒ 病灶在验证协议，
  **任何读清单改动都救不了**，必须恢复"看全尺寸图"的能力。
- 别指望靠减读清单治好"需要眼睛才能发现"的缺陷类。**先判断缺陷属于"先验驱动"还是"验证驱动"，再决定压哪个。**

## 遮挡类缺陷：正确解法是「几何判据」，不是「更多像素」

**案例**（EXP-01 / SC06 / 帧 690 = 23.0s）：论文卡（实心黑底 `Box fill="#000"`，`x=880,w=280`）
把主角「TLS 1.3」尾部盖住 39px。机制只有一行：
**主角入场 666、卡片入场 642，而卡片在 DOM 里排在主角之后 → 后出现的信息被先出现的东西压住。**

**四重独立证据（照这个套路取证，别只靠"我觉得"）**
1. **源码层序**：DOM 次序 = 屏幕叠加次序（无 `z-index`），对比两者入场帧 → 倒置。
2. **几何**：字宽**用真实字体实测**（PIL + `Audiowide`）得墨迹盒 `x[321,919]`，与卡片 `x[880,1160]` 求交 = 39px。
3. **像素**：帧 690/696「抢墨带 x[884,909)」白墨迹 C0 54% → C2F 1.3%（**−53pp**），而字心对照带只差 1.2pp
   → 排除运镜，坐实遮挡。
4. **历史对照**：C0 版同一镜头的**注释里就写着**「实测主角 x314–936，卡片 850–1149，重叠 86px」并已把卡右移到 910。
   → C2F 精确复现了**修复前的状态**。

**判据（可直接抄进构建契约）**
- **Z1 层序倒置（高）**：B 后入场却排在 A 之前（被 A 压住），且画面相交。
- **Z2 同帧叠字（中）**：两个可读文本入场帧相距 ≤6 帧、墨迹相交 >15%。
- **分级口径**：外扩区（墨迹 ⊕ 柔光）相交是检出下限；其中**墨迹也相交 ≥1200px² → 高**，
  仅柔光区相交 → **中**（压边/洗淡）。
> 柔光是加光的，不是遮挡的；把两者混在一级会让报告失去可操作性。

**实现六坑（全踩过）**
1. **入场帧要回溯 `const`**：`opacity={cardOp}`、`cardOp = clamp01((N-642)/16)` → 642。
   直接从 JSX 切片找 `N - \d+` 会漏。
2. **候选只能从「本元素起始标签」取**：切片里常含**下一个**元素的标签（因为 `<SoftIn>` 这类 wrapper 不被扫描），
   否则 pill1 会取到 pill2 的 `f0`（739 变 741）。
3. **外层 wrapper 的 `f0=` 取 `back` 窗口里最后一个**（最靠近、真正包住它的那层）。
4. **字宽必须用真实字体实测**，不要 `0.58em/字` 估；`letterSpacing` 按 CSS 也要计到每个字素后（含末字）。
5. **`y={210 + cardDy}` 这类「字面量+变量」取前导字面量**（动画偏移量远小于坐标）。
6. **退化矩形（解析失败）静默剔除并计入"盲区"**，不参与判定 —— **宁可漏，不要错**。

**两条硬教训**

**(A) 照抄历史修复值是危险的。** C0 当年把卡移到 `x=910` 就清了（C0 的 `letterSpacing=0` → 墨迹右缘 908.5）。
C2F 的共用件 `HeroTLS` 是 `letterSpacing=3` → 墨迹右缘 **919 > 910**，**仍然遮 9px**。
→ 必须在**当前实现**上重算：给定主角墨迹右缘 + 安全区右界，算出卡左缘下限（本次解：`x=930, w=270` → 墨迹重叠 **0**）。
**受益于几何判据的一点：它不只报"错"，还能报"差多少像素"。这是任何缩略图给不出的。**

**(B) 「0 命中」绝不等于「干净」——工具输出必须自带覆盖率。**
在 C0 源码上跑同一个审计器得 **0 命中**，但那是**假的**：C0 用 wrapper 局部坐标
（`<div style={{left:910, top:cardY}}>` 包一个 `<PaperCard x={0} y={0}>`）、主角是 `<CText cx={HERO.cx}>`，
**全都落在"未解析"里**（C0_G2 覆盖率仅 63.2%，主角压根没参与计算）。
→ **审计报告必须同时打印「可审覆盖率 = 已解析 / 内容对象」和「未解析清单」**，
否则使用者会把"没审到"读成"没问题"。**无覆盖是无声的**（与本节上文同源，这里要把它固化成工具的必备字段）。

**成本洞察（排档位时最有用的一个数）**
账本 B「图像重放代价 = 单张 tok × 张数 × **读图后剩余轮次**」里，真正贵的是**最后那一项**：
C0 = 6 张 × 1229 tok × **75 轮** = 829.5 万；C2 = 2 张 × 77 tok × **8 轮** = 1.85 万。
→ **在"尾部看"加图，比在"边做边看"加图便宜 9.4 倍。**
所以若要定向恢复看图能力（1 张整帧缩略 + 1 张审计器点名区域的 1:1 裁剪），
账本 B 只从 1.85 万 → 3.23 万（**×1.75**），仍只有 C0 的 **0.4%**；
而账本 A 只 +490 tok/组（**+5.3%**，相对 C0 仍 −76%）。
**结论：把几何类缺陷重新变成"可被门禁拦住"的东西，几乎不花钱。**

**附带一条工程前提（建议写进构建规范）**
静态审计的可靠性依赖"坐标可静态求值"。本次 74% 覆盖率里，剩下 26% 的盲区**几乎全是可修的**：
`BigNumber / Envelope / MsgCard / ClientBox / TechText` 补进**图元量尺表**（每个共用件渲一帧 + DOM 探针读
`getBoundingClientRect()`，**一次性、零图像 token**），`cx={VAR}` 这类则立一条规范：
**所有内容元素的矩形必须可由源码字面量求得（否则进 `LAYOUT` 表）。**
→ 这条规范几乎零成本，却是"零图像几何审计"能否成立的前提。

**Windows 工程坑（本次浪费了两次往返）**
PowerShell 里 `& python ... | Out-File`：python 的 UTF-8 字节**会先被控制台按 GBK 解码**，中文全变乱码，
连 `_zlog.txt` 都会被 Read 工具判成 binary。
→ 规矩：**让脚本自己写 UTF-8 文件（`open(..., 'w', encoding='utf-8')`），stdout 只输出 ASCII**
（`print(txt.encode('ascii','replace').decode())`）。别指望管道。

## 新建 `anything2explainer-lite`（C2 固化档）：把「只有眼睛能发现的事」变成源码里可算的数字

> 承接上一节。R先生 定案：**不做 C1 对比实验、不修 SC06 重渲**，只把 C2 固化 + 门禁整合，做成一份性价比更高的 lite skill。

### 1. 架构决策（下次做「档位固化」直接照抄）

- **独立成 skill，不作为原 skill 的一个档位。** 理由：原 `SKILL.md` 的工作流正文写的是 **C0 语义**（每镜 ≥6 张 still、3 轮 QC、派单附 12K 的 `agent-build-rules.md`）。让 agent 读着 C0 指令再"记得覆盖"是**真实的失败源**。
- **不复制引擎。** `template/` 17.6 MB，其中 `NotoSansSC.ttf` 占 **16.95 MB**，代码只有 0.24 MB。`new_project.py` 用 `_env.package_root()` **从自身位置推导模板根** → lite 按引用用引擎，零重复；且 `new_project.py` **连 `scripts/` 一起复制**，新项目天然带新门禁。
- **lite 只带协议**：`SKILL.md` + 4 份 reference + 1 个 bootstrap 脚本。

### 2. 「没跑」必须是一种独立状态，不能等于通过

`lite_gate.py` 四轴合并 + 一个退出码。关键设计：
- 构建期只有 2 轴可跑 → 另 2 轴标「**未跑**」（**独立状态，不等于通过**），rc=1（除非 `--allow-partial`）。
- `frame_metrics` 设「**仅报告**」不门禁 —— 它的"高"是**相对量**（主角是"最大物体"单选取；C0 基线本身就有 1 条"空场"高）。
- 一开始我把"跑了但没设门禁"误标成"未跑"，**报告会说谎** → 必须把「未跑 / 仅报告 / 通过 / 不通过」做成**四个**不同状态。

### 3. 关键实测：**注册表救不了「对象属性访问」**（推翻上一节的乐观预期）

上一节我写「剩下 26% 盲区几乎全是可修的，补进图元量尺表即可」。**实测不成立**：

| 做法 | 覆盖率 |
|---|---|
| C2F 基线 | 74.0% |
| + `zorder_parts.json` 登记 `BigNumber` | **80.0%（仅 +6pp）** |
| 剩下 10 个盲区 | `MsgCard x={CARD.x + cardDx}`（**动态偏移**）· `ClientBox cx={CLIENT.cx}` / `Envelope`（**对象属性访问**） |

→ **这些静态不可解，注册表救不了。** 唯一解是**把几何抽成扁平局部常量**：
`const CARD_X = 420; const CARD_W = 460;` → `x={CARD_X}`。
→ **结论：注册表是补丁，坐标扁平化才是解药。覆盖率上不去时，先怀疑源码写法，不要怀疑审计器。**

### 4. 交付物必须有「列」，否则信息不传承（本档最重要的设计）

`BUILD_NOTES` 新增**三列**：**主体墨迹盒 / 最大重叠 / Z1·Z2 命中数**。
证据：C0 的构建者**算过**重叠并写进注释（「卡片 850–1149，重叠 86px」）—— 但**没有列可填** → 信息留在注释里、没进交付物 → 换版重建时**没有任何机制把它带回来** → 同一个 bug 精确复现。
→ **有列才有承接。凡"这次算过但没处可写"的数字，下次一定丢。**

### 5. 门禁自身也要防「静默给错读数」

`lite_gate` 解析覆盖率时**优先读 JSON**（`totals.coverage_pct`）；正则兜底**必须锚定「可审覆盖率」字样**。
原写法 `re.search(r'=\s*([\d.]+)%', 报告)` 会匹配到报告里**任意一个** `= 12.3%` → **静默给出错读数 → 错读数导出错理由 → 骗人**。
→ 与「没覆盖比假阳性更危险」同源：**读数错了不会响，只会让人信。**

### 6. 交付物清单（供复用）

- `anything2explainer-lite/`：`SKILL.md` · `scripts/lite_bootstrap.py` · `reference/{build-contract-lite.md, qc-lite.md, prompts-lite.md, lessons-lite.md, ENGINE.md}`
- 原 skill 侧：`template/scripts/{zorder_audit.py, lite_gate.py}`（**住在引擎里**，因为要能被 `lite_gate.run()` 当兄弟进程调用）· `SKILL.md` 加 lite 路由 · 「三根质量轴」→「完整版三根 / **lite 四根**」。

### 7. 仍然**未验证**的（不要当成结论）

- 覆盖率 ≥90% 需实际做 §13 坐标扁平化（本次只证了「注册表 +6pp」这个边界）。
- 方案四（渲染期 DOM 探针，抓**像素级**柔光遮盖）**未做工程验证**。
- lite skill **尚未端到端实跑**（R先生将用新 agent 装配测试）。

## 追加：把 lite 版做成「下载即用」—— 独立性 vs DRY 的取舍

> R先生实测反馈：**「agent 说 lite 版本不包含引擎，他需要去原 skill 里复制 Remotion 工程才能编译。我们需要的是完全独立的 lite 版本，是一个别人只下载该 lite 版就能直接用的 skill。」**

### 教训 1：「要 DRY」还是「要独立」必须先问清楚
上一轮的决策是**不复制引擎**（模板 17.6 MB，复制 = 改两处 → 迟早漂移），并在文档里写明了这个取舍。结果 R先生 的真实需求是**下载即用** —— 这个取舍从一开始就不成立。
→ **架构取舍不能只在文档里自证合理，必须回到"使用者怎么拿到它"这个场景上问一句。** 尤其当「使用者」可能是**第三方**（别人下载）而不是本机时，任何"本机另一处已有"的假设都不安全。

### 教训 2：依赖是**四层**的，不止引导脚本一处
只修 `lite_bootstrap.py` 的引擎查找顺序是不够的。同一份 skill 里藏着四层外部依赖：
1. **引擎** —— 引导脚本去找原 skill 的 `template/`
2. **参考文档** —— `SKILL.md` 的阶段 1–4 让 agent 读原 skill 的 `research-brief.md` / `style-guide.md` / `narration-storyboard.md`
3. **示例资产** —— `build-contract-lite.md` §11 的模式路由指向 `examples/rag/shots_src/`，§2 指 `examples/rag/frames/ref_*.jpg`
4. **交叉引用** —— 文档抬头引用了未打包的 `agent-build-rules.md` / `build-contract.md`

→ **做"独立性"检查的正确方法**：把待打包目录整体 grep 一遍 `原skill名`、`../`、被引用文件名，逐条判断「这个文件在不在包里」。**只检查入口脚本必然漏掉第 2–4 层。**

### 教训 3：复制别人的东西时，**授权与引用必须跟包走**
模板内含 4 款字体（OFL 授权），仓库根有 `LICENSE` 与 `CITATION.cff`。复制引擎到另一个 skill 时若不带上它们，就不是"独立"，而是"剥离授权"。
→ 打包时把 `LICENSE` / `CITATION.cff` / 字体 `LICENSE.md` 与代码**同等对待**。

### 教训 4：包内**过时的上游文档**比缺失更误导
上游 README 描述的是完整版布局（列了 `agent-build-rules.md` 等未打包文件、安装路径写的是 `anything2explainer`）。留在包里，下载者会照着它去找不存在的文件。
→ **归档改名**（`UPSTREAM_README.md` / `UPSTREAM_README_zh.md`）并在新 README 里说明，或直接删除。同理适用于历史派单文件（`examples/**/AGENT_*_RULES.md`）。

**加一条（2026-09-12 补）**：归档还不够，**归档件的语言切换内链也要改**。上游 `README_ZH.md` 顶部写的是 `[English](README.md)` —— 一旦本档自己的 `README.md` 占了这个名字，这个链接就指向**我们的** README 了。归档时这类相对链接会静默指向错误目标。
→ 归档件顶部加一句"这是存档、可能失效"，并把语言切换链接改成归档件之间的互链。

### 教训 6：**发布前必须扫本机路径**
移植/调试期为了方便写死的绝对路径（解释器、Node、ffmpeg、上游检出目录）会**原样进包**，一推上 GitHub 就泄露用户名、目录结构与本机工具链布局（哪怕不含凭据，也是不该公开的信息）。
→ 发布前跑一次 `grep` 扫 `用户名` / `HOME` 路径 / `.workbuddy` 等标记；发现即改为 **环境变量优先 + 通用兜底**（`A2E_PYTHON` → `PATH` → 系统默认安装位置）。已发现的实际形态：5 个 `.sh` 的解释器候选、`_env.py` 的 `_FALLBACK_DIRS`、SKILL/ENGINE/WINDOWS-PORT 三份文档里的示例路径。
→ 顺手扫一遍**凭据类关键词**（`api_key` / `token=` / `password` / `PRIVATE KEY`）与跨项目字样，确认没有串味。

### 教训 5：给"完整性"做一个**一键自检**
`lite_bootstrap.py --check` 校验 17 个引擎关键件 + 4 份协议 + 10 项软资产，输出「引擎来源：本 skill 自带 / 自带件检查：✓ 全部就位 / 独立性自检通过 ✓」。
→ **"独立"必须可被一条命令证明**，否则只能靠人肉记忆。这比在文档里声明"本 skill 是独立的"有用得多。

### 附带修掉的一处不自洽
引擎里两个脚本的文件头 docstring 引用了未打包的 C0 文件（`agent-build-rules.md` / `agent-qc-rules.md`）。`frame_metrics.py` 与 `zorder_audit.py` 已改指包内存在的文档；该修补记在 lite 的 `reference/ENGINE.md §5`，避免下次同步引擎时被静默覆盖。


### 教训 7：Windows 上推仓库，**换行符必须先立规矩**（`.gitattributes`）
本机 git 全局配置是 `core.autocrlf=true`。若不显式约束，**检出时会把 `.sh` 写成 CRLF**——
`#!/usr/bin/env bash` 后面多一个 `\r`，在 Git Bash / Linux / macOS 上直接 `bad interpreter`，脚本全废，
而在 Windows 上写这些脚本的人**看不到任何异常**（本地用 `.py` 调，根本走不到 `.sh`）。

→ 仓库根放 `.gitattributes`，显式点名：`*.sh text eol=lf`（可执行脚本必须 LF）、
源码与文档 `eol=lf`、字体图片 `binary`（禁止任何转换，否则 TTF/JPEG 损坏）。

**验证要认对象，不认命令**：
`git ls-files --eol` 报 `i/lf w/crlf` 才是真相；而 `git show :path` / `git cat-file -p :path`
**会施加检出转换**，看出来的 CRLF 是假的。要读原始对象得用
`git cat-file blob $(git rev-parse HEAD:<path>)`——实测该口径 CRLF 计数为 0，与 `i/lf` 一致。

→ 通用原则：**判断仓库里到底存了什么，只信 blob 对象本身。**
